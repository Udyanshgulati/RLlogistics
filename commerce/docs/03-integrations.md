Recommendation: get written quotes and API sandbox access from **DHL Express India and FedEx India first** (both have documented rate/ship/track APIs and Delhi presence), and Shiprocket X as a comparison for lanes where a direct contract is expensive. Choose by actual quoted rates, transit days and pickup cut-off for the warehouse PIN — not by this table.

### Live rates vs defined express tiers at launch

| | Defined express tiers (zone × weight band, from the signed rate card) | Live carrier rates at checkout |
|---|---|---|
| Accuracy | Good if bands follow the contract; dimensional weight and remote-area surcharges must be in the bands or absorbed | Exact for the quoted parcel |
| Checkout speed / resilience | No external call at checkout | Carrier API latency and outages hit checkout |
| Build effort | WooCommerce shipping zones + table (native) | Carrier adapter + caching |
| Promise | "Express, typically N–M days" only where the contract states it | Carrier's own estimate per quote |

**Safest launch:** defined express tiers priced from the actual contract, shipped only to an explicit destination allowlist (`markets.json → shipping.destination_allowlist`); bookings, labels and tracking through the carrier API from the hub. Add live rates once the adapter has passed sandbox tests. The hub's `ExpressSelector` already enforces: express only, no silent downgrade, "rates unavailable" instead of an invented price, and "Estimated" unless the carrier guarantees and the business opts in.

Data the hub already holds per SKU for customs and quotes: weight, L×W×H, declared value, HS code, origin country. Shipment quotes refuse to run while the warehouse address or a needed HS code is missing (`ParcelRequest::problems`).

Handled by the system: no card data ever touches our servers (hosted/tokenised gateway flows); duplicate payment webhooks are idempotent (reservation confirm is a no-op the second time); delayed payment confirmation keeps the stock hold and the expiry worker asks the storefront before releasing; payments arriving after a hold lapsed re-take stock if available or are flagged "paid, no stock" for a person; refunds and partial refunds are requested once through WooCommerce (`api_refund`) and marked refunded only when the storefront confirms.

## 3. Multi-currency

The five currencies are tracked separately:

| Currency | Where it lives |
|---|---|
| Display | Shopper's market (`markets.json`), shown with the rate date; stored on the order (`display_currency`, `display_fx_rate`, `display_fx_as_of`) |
| Checkout transaction | The order's `currency` — chosen by `CheckoutPolicy` from currencies a **verified** gateway can charge |
| Gateway processing | Same as checkout unless the gateway converts (gateway statement is the record) |
| Settlement | Per gateway contract (normally INR) — from gateway settlement reports |
| Reporting | Reports group by order currency and never add currencies together |

**Safest initial implementation:** charge in **INR** on all storefronts, show converted prices as clearly labelled estimates ("Prices shown in USD are estimates; you will be charged ₹X"), with ECB reference rates refreshed daily and withheld if older than 48 h (no hard-coded rates; tested). Phase 2: add USD/GBP/EUR as checkout currencies on one gateway once it confirms them in writing, using **WooCommerce Multilingual & Multicurrency (free)** for per-currency checkout rather than custom code, with market prices set by the brand (`market_prices`) instead of floating conversions.

## 4. Email

Email is the primary channel; the hub will be the only sender of order emails (WooCommerce customer order emails switched off to avoid duplicates; account/password emails stay in WordPress via an SMTP plugin pointed at the same provider).

| Provider | Price (checked) | Notes |
|---|---|---|
| Amazon SES | **$0.10 per 1,000** emails à la carte; attachments $0.12/GB; dedicated IP $24.95/month ✔ (aws.amazon.com/ses/pricing) | Bounce/complaint notifications via SNS; per-brand verified domains with DKIM; region choice (Mumbai available — verify) |
| Brevo | Free tier and paid plans — verify current limits | Simpler set-up; marketing features we must keep separate |

Recommendation: **Amazon SES** (lowest usage cost at this volume). Required set-up per brand domain: SPF include, DKIM (Easy DKIM), DMARC starting at `p=none` with reporting, then tighten; custom MAIL FROM domain; bounce and complaint handling to a suppression list. Events and status: see doc 10 — the engine is **not built yet**; queued notifications wait in the outbox and fail visibly.

Required events: order placed, payment confirmed, processing, dispatched (with tracking), tracking update, delivery exception, delivered (when the carrier reports it), cancelled, refund completed, return opened/updated. All already queued by the hub at the right moments, de-duplicated per order and event.

## 5. WhatsApp (optional)

Official WhatsApp Business Platform (Cloud API, direct from Meta — no BSP fee). Pricing ✔ (developers.facebook.com/docs/whatsapp/pricing): **per delivered message** since 1 Jul 2025, by category (marketing, utility, authentication, service) and recipient country; **utility messages inside the customer-service window are charged again from 1 Oct 2026**; 1,000 free service messages per number per month. Country rates: Meta's rate card — verify per launch market.

Rules: approved templates only; opt-in captured at checkout (unticked by default, per brand, stored with time and wording); STOP/opt-out honoured from webhooks; transactional only — no marketing without separate consent; channel availability configured per market (`communication.whatsapp`).

## 6. Tax, customs and compliance — needs professional confirmation

Technical support exists; **decisions below are for the client's CA / customs broker / lawyer**:

| Topic | What the system supports | Decision needed |
|---|---|---|
| Export registration | — | IEC for each exporting entity; which legal entity sells for each brand |
| GST on exports | Tax stored per order; tax display per market | Zero-rated export under LUT vs IGST paid and refunded; e-commerce export documentation; e-BRC/FIRA from gateways |
| Destination VAT / sales tax | `duties.mode` per market, shown at checkout | e.g. UK/EU low-value import VAT rules, US de-minimis status at launch time — must be checked per market when launching |
| Duties | DAP by default ("charged by the carrier on delivery") | DDP only if a carrier contract supports it and the business accepts the cost |
| HS codes / origin | Stored per product; required before international quotes | Classification by a customs adviser |
| Restricted goods / destinations | Per-product allow/block lists; destination allowlist; brand-level market switches | List of restricted items and countries |
| Privacy | Minimum customer data, PII permission, view audit | Privacy policy per brand (India DPDP Act; GDPR/UK GDPR for EU/UK shoppers) |
| Returns policy | Returns workflow with inspection | Policy text per brand and market |
